# Clean Code Commenting Guidelines

This skill defines rules for comment generation in source code by AI coding assistants (including Cursor and Antigravity).

## Core Principles

### 1. Code is the Documentation
- Code should be clean, readable, and self-documenting. Use descriptive variable, class, and method names rather than explaining what the code does in inline comments.
- **Bad:**
  ```php
  // Increment bid count by 1
  $auction->bid_count = $auction->bid_count + 1;
  ```
- **Good:**
  ```php
  $auction->incrementBidCount();
  ```

### 2. Explain "Why", Not "What"
- Comments should explain the rationale behind non-obvious design choices, business rules, or complex workarounds. Never write comments that merely repeat the code.
- **Bad:**
  ```javascript
  // Set points form field value to user points
  form.points = user.points_balance;
  ```
- **Good:**
  ```javascript
  // Pre-fill with the user's current points balance to streamline the bidding flow.
  form.points = user.points_balance;
  ```

### 3. Avoid Dummy or Placeholder Comments
- Do not add section dividers, file headers, or step-by-step numbers (`// 1. Verify...`, `// 2. Save...`) unless they are required by a very complex algorithm.
- Do not leave empty boilerplate comments (`//`) generated by CLI scaffolders.

### 4. Prefer Standard Docblocks
- Use PHPDoc blocks for classes and methods to define parameter types and return types, rather than inline comments.
- Follow JSDoc/TSDoc conventions in JavaScript and TypeScript.
